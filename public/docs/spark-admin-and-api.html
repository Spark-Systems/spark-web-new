Admin guide & API specification

How the content admin works, and the exact API a backend must provide so the website and admin can run on it. Written for content editors (section 2) and the backend team (sections 3–11).

Frontend: Next.js 16 (website + /admin)Content language: EnglishAdmin UI: English / Arabic

1. Overview

The project has two faces in one Next.js app:

  • The website (/, /about, /solutions, /services, /work, /contact and the detail pages). Pages are pre-rendered and only re-rendered when content is published.
  • The admin (/admin). A browser app that edits every piece of website content through a JSON API.

Today that API runs inside the same app (/api/admin/*, /api/v1/*) and stores content as JSON files (Vercel Blob in production). It is a working reference implementation: a backend that implements the contract below can replace it without changing the admin screens or the website pages.

Adminbrowser, /admin
→ Admin API (Bearer token) →
Backendyour stack
→ Public API (published only) →
WebsiteNext.js, pre-rendered

On publish the backend calls the website’s revalidation webhook, so the new content appears within seconds.

2. Using the admin

2.1 Signing in

  1. Open https://<site>/admin and sign in with your email and password.
  2. The first admin account is created from the ADMIN_EMAIL / ADMIN_PASSWORD settings the first time someone signs in with them. Change the password under Profile (avatar menu, top right).
  3. Switch language (English / العربية) and light/dark from the top bar.

3. API conventions

3.1 Base URLs

Paths below are relative to those bases. Please keep them; only the host/base prefix may change.

3.2 Format

  • JSON in and out, UTF-8. Dates are ISO-8601 strings in UTC (2026-10-06T13:02:06.492Z).
  • Top-level record fields are snake_case (has_detail, created_at). Page content blocks are camelCase (titleLines, ctaLabel) because they reuse the website’s own types unchanged. Keep both exactly as specified.
  • IDs are opaque strings with a readable prefix (sol_…, svc_…, prj_…, cli_…, par_…, off_…, usr_…, enq_…, act_…). Keep the existing IDs when importing.
  • Writes are full replacements (PUT sends the whole record/page), not patches.
  • Empty optional text is ""; optional objects are omitted (not null) unless the model says | null.

3.3 Lists, errors

Every admin list endpoint takes the same query and returns the same shape:

GET /solutions?page=1&page_size=10&sort=order&order=asc&q=tick&status=published,changed&flagship=yes

{
  "data": [ /* rows of this page */ ],
  "total": 13            // rows matching search + filters, across all pages
}
  • page 1-based; page_size 1–100 (default 10).
  • sort is any row field; order asc|desc.
  • q is a case-insensitive “contains” search over the fields listed per endpoint.
  • Facet filters are comma lists; values within one facet are OR, different facets are AND.

Every error has this body (fields other than message are optional):

{
  "message": "Some fields are invalid",     // human-readable, shown in the admin
  "code": "validation",                     // machine-readable reason
  "field": "slug",                          // for single-field errors (409 slug_taken…)
  "issues": [                               // for 422 validation
    { "path": "detail.features.items.0.title", "message": "Required" }
  ]
}

The admin highlights the field at each path (dotted, array indexes as numbers; page paths are prefixed content.).

3.4 Authentication

  • POST /auth/login returns an access token (15 min) and a refresh token (7 days). JWTs are fine; the admin treats them as opaque strings.
  • The admin sends Authorization: Bearer <access_token>. On a 401 it calls /auth/refresh once, retries, and signs the user out if that fails.
  • Changing a password must invalidate all older tokens of that user.
  • Please rate-limit failed logins per email (the reference locks an email for 15 min after 8 failures).

4. Drafts & publishing

Every list item and every page is stored as an envelope with two copies of its content:

{
  "id": "cli_001",            // list items only
  "draft":     { /* T: what the admin edits */ },
  "published": { /* T: what the website shows */ } | null,
  "created_at": "…", "updated_at": "…",
  "published_at": "…" | null,
  "updated_by": "Spark Admin"  // name of the last person who saved
}
  • Save (PUT) replaces draft, sets updated_at/updated_by.
  • publish copies draft → published, sets published_at.
  • unpublish sets published to null (lists only).
  • discard copies published → draft.
  • status is derived on read: draft when published is null; published when both copies are deep-equal; otherwise changed.

The admin API returns the draft flattened with the publication fields (CollectionRow<T>); the public API returns only published copies, sorted by order ascending.

{
  "name": "Ministry of Foreign Affairs",
  "logo": {
    "src": "/uploads/images/clients/mofa-6d5a47b7.webp",
    "width": 289,
    "height": 91,
    "blurDataURL": "data:image/webp;base64,…",
    "blurWidth": 10,
    "blurHeight": 3
  },
  "link": "",
  "show_name": false,
  "invert": false,
  "order": 10,
  "id": "cli_001",
  "status": "published",
  "created_at": "2026-10-06T13:02:06.492Z",
  "updated_at": "2026-10-06T13:02:06.492Z",
  "published_at": "2026-10-06T13:02:06.492Z",
  "updated_by": "Initial content"
}

Please also keep a few previous versions of each document (the reference keeps the last 10) and an activity log entry for each create / update / publish / unpublish / discard / delete / login (ActivityEntry).

6. Uploads

POST /uploads            (multipart/form-data)
  file   = <binary>
  folder = "solutions" | "services" | "work" | "clients" | "partners" | "offices" | "pages" | …   ([a-z0-9-], ≤ 40)

201 →
{
  "url": "https://cdn…/images/solutions/ticketing-958ca756.webp",  // same as src
  "src": "https://cdn…/images/solutions/ticketing-958ca756.webp",
  "width": 2400,
  "height": 1350,
  "blurDataURL": "data:image/webp;base64,UklGR…",   // ~10px WebP, raster images only
  "blurWidth": 10,
  "blurHeight": 6
}
  • Max 4 MB. Detect the type from the file’s bytes, not its name: JPEG, PNG, WebP, GIF, AVIF, TIFF, or SVG.
  • Raster images: apply EXIF rotation, fit inside 2400×2400 (never enlarge), save as WebP (quality ~82), return the real output width/height and a tiny blur preview.
  • SVG: reject files containing <script, <foreignObject, on…= handlers, javascript:, <iframe|embed|object. Return the SVG’s width/height (viewBox). No blur.
  • File names must be unique and immutable (cache for a year). The returned object (minus url) is stored as-is wherever the models say UploadedImage; the website uses width/height for layout and the blur for placeholders.

7. Website (public) API

7.1 Endpoints

These return published content already assembled into the website’s page models (section 9 “Website models”). How each page is assembled:

  • home = pages/home + clients.clients (all clients) + clients.partners (all partners) + contact (from pages/layout.contact).
  • about = pages/about + client logos + partnerships.partners = the first two partners, each with label = pages/about.partnerships.label (omit partnerships if fewer than two) + contact copy.
  • solutions = page copy + flagships.items (solutions with flagship) + catalog.items (all solutions).
  • services / work = page copy + all services / projects as summaries.
  • contact = page copy + offices + enquiry.email (from layout) + enquiry.socials (settings social links that have a URL).
  • layout = company (name, description from settings meta; email, phone, foundedYear from layout), keywords, menu, footer, contact copy, solutions, offices, partners, socials.
  • An item’s hasDetail is has_detail && detail != null. Detail pages take slug and overview.name from the item and contact from the layout.
  • next project (work detail): the next published project that has a case study, wrapping around; if it’s the only one, { name: "All work", category: "See every project", image: <another project's image>, href: "/work" }.

7.2 Preview (drafts)

For preview mode the website needs the same public endpoints to return drafts (unpublished items included) when called with an editor’s token, e.g. GET /v1/pages/home?preview=true + Authorization: Bearer …. Responses must not be cached by a CDN in that case.

7.3 Caching

The website caches public responses until you call the revalidation webhook, so they can be served with normal caching headers.

8. Revalidation webhook (backend → website)

After anything that changes published content (publish, unpublish, delete of a published item, settings change), call:

POST https://<website>/api/revalidate
Authorization: Bearer <REVALIDATE_SECRET>      // shared secret, agreed between teams
Content-Type: application/json

{ "resource": "solutions", "id": "sol_ticketing", "action": "publish" }

→ 200 { "revalidated": true }

The website refreshes all pages (they share the menu/footer data). We will add this endpoint when switching to your backend; until then the reference implementation revalidates internally.

/**
 * The detail page of a list item (`detail`) is validated only while it's
 * switched on (`has_detail`). Switched off, whatever was there is kept as is
 * (so switching back restores it) and the website ignores it.
 */
function withDetailPage<D extends z.ZodType>(detail: D) {
  return <S extends { has_detail: boolean; detail: unknown }>(value: S, ctx: z.RefinementCtx) => {
    if (!value.has_detail) return { ...value, detail: (value.detail ?? null) as z.output<D> | null };
    if (value.detail === null || value.detail === undefined) {
      ctx.addIssue({ code: "custom", path: ["detail"], message: "Add the detail page content, or turn off the detail page" });
      return z.NEVER;
    }
    const parsed = detail.safeParse(value.detail);
    if (!parsed.success) {
      for (const issue of parsed.error.issues) {
        ctx.addIssue({ code: "custom", path: ["detail", ...issue.path], message: issue.message });
      }
      return z.NEVER;
    }

  };

11. Handover checklist

Backend team delivers

  1. Implement the admin API (section 5) with the exact paths, payloads and error shape. Allow CORS from the admin origin, Authorization: Bearer auth.
  2. Implement the public API (section 7), returning published content only, already assembled into the page models (lists filled in, as described).
  3. Store every list item and page as a draft/publish document (section 4); compute status on read.
  4. Implement uploads (section 6): validate by content, resize to ≤ 2400 px, WebP, return width/height and a ~10 px blur preview. Serve uploads from a CDN and tell us the host.
  5. On every publish / unpublish / delete / settings change, call the revalidation webhook (section 8).
  6. Import the starting content from the data/ folder of the repo (section 10) so the site looks the same on day one.
  7. Send us: base URLs (staging + production), the CDN host for images, the webhook secret, and a test admin account.

Frontend then changes

  1. src/admin/lib/api/config.ts → API_BASE_URL = your admin base URL. Keep Google Analytics on our own /api/admin/analytics/* routes (we’ll split the client back into two).
  2. src/server/content/pages.ts → swap the database reads for fetch calls to your public API (the getters in src/lib/api/pages.ts keep their signatures, so no page changes).
  3. Add POST /api/revalidate on the website (section 8) and drop our in-process revalidation.
  4. Preview mode: /api/preview will validate the token with your GET /auth/me, and in preview the site will call your API with the editor’s token to read drafts (section 7.2).
  5. Add your image CDN host to images.remotePatterns in next.config.ts.
  6. Remove src/server/* and src/app/api/admin/* (except analytics) once everything runs against your backend.

Questions or changes to the contract: agree them before implementing, since the admin screens validate and render against these exact shapes.
