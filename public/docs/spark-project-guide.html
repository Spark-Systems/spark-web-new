Spark Systems

Project guide: website, admin & backend

How the Spark Systems website and its content management fit together: what runs where, how to run and configure it, how content reaches the site, how it's deployed and secured, and how to fix the usual problems.

For developers and whoever maintains the servers. For every endpoint and data model in detail, see the Admin guide & API specification.

1. Overview

The project is two applications that work as one:

Website: spark-web

Next.js 16, React 19, TypeScript, Tailwind CSS 4. The public marketing site and the admin panel at /admin. Hosted on AWS Amplify.

Backend: backend (spark-backend)

Node.js 22 and TypeScript, no framework. Stores content, accounts, messages and pictures; serves the admin API and the public API. Hosted on Plesk (Windows, IIS + iisnode).

Everything shown on the site is managed in the admin: pages, solutions, services, projects (work), clients, partners, offices, jobs, insights and site settings. Visitors' contact messages and job applications land in the admin too.

2. Architecture

Browsers only ever talk to the website. The website forwards admin calls, public API calls and pictures to the backend, so everything appears on one domain: no CORS, and sign-in keeps working.

Who calls whom

From → toWhatHow it's authorised
Browser → websitePages; admin screens; /api/admin/*, /api/v1/*, /uploads/* (forwarded to the backend by next.config.ts rewrites)Admin calls carry Authorization: Bearer <access token>
Website server → backendPage content (/api/v1/pages/…), detail pages, form submissions, drafts for preview modex-spark-secret header (shared secret)
Backend → websitePOST /api/revalidate after every publish or delete, so the site rebuilds its pagesx-spark-secret header (shared secret)
Browser → backend directlyNot used by default. Possible with NEXT_PUBLIC_API_URL (see website settings)CORS allowlist on the backend

4. Running locally

Requires Node.js 22 or newer. Start the backend first: the website reads all its content from it, both while running and when building.

  1. Backend. In backend/, copy .env.example to .env and fill in SPARK_SHARED_SECRET, AUTH_SECRET, ADMIN_EMAIL and ADMIN_PASSWORD. Then: 
    npm install
npm run dev        # http://127.0.0.1:4000 (restarts on changes)
  2. Website. In spark-web/, copy .env.example to .env.local and set SPARK_SHARED_SECRET to the same value as the backend's. The backend address comes from .env.development. Then: 
    npm install
npm run dev        # http://localhost:3000
  3. Sign in at http://localhost:3000/admin. With no users yet, signing in with ADMIN_EMAIL / ADMIN_PASSWORD creates the first admin. After that, manage accounts under Users.

Generate a secret with:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

7. Publishing & caching

Every item and page has a draft (what the admin edits) and a published copy (what the site shows). Its status is draft (never published), published, or changed (published, with unpublished edits).

Admin actionEffect on the site
SaveNone: only the draft changes
CreateNone, unless created with publish
PublishThe draft becomes the published copy; the site refreshes
UnpublishRemoved from the site; the site refreshes
DiscardThe draft goes back to the published copy
DeleteRemoved everywhere; the site refreshes
Save settingsThe site refreshes

How the site refreshes

  1. The website pre-renders its pages and caches the content it reads from /api/v1 (cache tag content).
  2. After a publish, the backend calls POST {FRONTEND_URL}/api/revalidate with x-spark-secret. It doesn't wait for the answer: the save has already succeeded.
  3. The website checks the secret, drops its cached content and pages, and rebuilds them on the next visit.
  4. Safety net: cached content is refreshed every 5 minutes anyway (MAX_AGE in lib/api/pages.ts, revalidate in app/(site)/layout.tsx). If a refresh call is lost, changes still appear within a few minutes.
Preview modeFrom the admin, /api/preview?path=/about turns on Next.js draft mode for a signed-in user: the site then reads drafts fresh from the backend (with ?preview=1 and the shared secret) and shows a preview bar. /api/preview/exit turns it off.

Each deploy starts with a fresh cache, because the build time is part of every cache key.

8. Images & uploads

  • Pictures are uploaded with POST /api/admin/uploads (editors), at most 4 MB.
  • The file's contents decide its type, never its name. JPEG, PNG, WebP, GIF, AVIF and TIFF are scaled to fit 2400 px, converted to WebP (quality 82) and stored with a small blurred preview. SVGs are kept as they are, but only without scripts, event handlers or embedded content.
  • Pictures are stored under uploads/images/<folder>/ with a unique name and served by the backend at /uploads/…, cached for a year.
  • Content stores pictures as /uploads/… paths. The site forwards /uploads/* to the backend.
Amplify's image optimizerOn Amplify, next/image uses Amplify's own optimizer, which can't read /uploads/… through the forwarding. In production, lib/api/backend.ts therefore turns those paths into https://new-spark26.spark-sys.com/uploads/…, and next.config.ts allows that host in images.remotePatterns. Locally they stay relative.

CVs from the careers form (PDF or Word, up to 4 MB) are stored in data/cvs/, never on a public URL. Signed-in users download them from the application's page.

10. Security

Sign-in

  • Passwords are hashed with scrypt (salted, cost stored with each hash).
  • Sign-in returns an access token (15 minutes) and a refresh token (7 days), both HS256-signed with AUTH_SECRET. The admin keeps them in cookies and sends the access token as Authorization: Bearer; on a 401 it refreshes once, then signs out.
  • Changing a password signs out every other session (tokens carry a version).
  • Brute-force brake: 8 failed attempts per email, or 30 per address, block further attempts for 15 minutes. Response times don't reveal whether an email exists.
  • Roles are checked on every admin endpoint (see Roles).

HTTP protection (backend)

  • CORS allowlist: only FRONTEND_URL and CORS_ORIGINS (plus localhost:3000 in development). Preflights from other origins get a 403. x-spark-secret is never accepted from browsers.
  • Headers on every response: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer, Strict-Transport-Security, Content-Security-Policy: default-src 'none', Cross-Origin-Resource-Policy; admin answers are Cache-Control: no-store.
  • Limits: request bodies up to 10 MB (enforced while reading, chunked or not); uploads and CVs up to 4 MB; header and request timeouts against slow clients; malformed hosts and paths get a 400.
  • Forms: 5 submissions per sender per 10 minutes, plus a hidden honeypot field (website) that silently drops bots.
  • Files: storage keys are validated so no path can leave the data or uploads folder; uploaded SVGs can't run scripts.
  • IIS: web.config hides .env*, data, dist, node_modules and removes X-Powered-By.
Known limits
  • Rate limits are kept in memory, per server instance, and are keyed by X-Forwarded-For, which a client can fake unless a proxy in front overwrites it.
  • Logging out doesn't revoke refresh tokens; only a password change (or a new AUTH_SECRET) does.
  • Tokens are in cookies readable by page scripts, so a cross-site scripting bug on the site could expose them.

11. Deployment

Backend on Plesk (Windows, IIS + iisnode)

  1. Build and package locally: 
    cd backend
npm run package     # builds dist/server.mjs and spark-backend-update.zip
    The zip holds app.js, web.config, .env.production, package.json, package-lock.json and dist/.
  2. Upload and extract the zip into the site's folder. Never overwrite .env, data/ or uploads/ on the server.
  3. Install runtime packages (sharp, Google Analytics) on the server: npm ci --omit=dev.
  4. In Plesk → Node.js, the Application Startup File is app.js. Restart the app (or touch web.config).
  5. Check https://new-spark26.spark-sys.com/health returns {"ok":true}.

The server's own .env must contain AUTH_SECRET, SPARK_SHARED_SECRET (same as Amplify's), and the first-admin settings if needed. Leave FRONTEND_URL out so .env.production supplies it.

Website on AWS Amplify

  1. In Amplify → Hosting → Environment variables, set SPARK_SHARED_SECRET (same value as the backend's). Optionally set BACKEND_URL to override .env.production.
  2. Push to the connected branch. amplify.yml writes the secret into .env.production before npm run build, because Amplify only gives console variables to the build, not to the running site.
  3. The backend must be up during the build: pages are pre-rendered from its content.
  4. After deploying, publish something in the admin and check it appears on the site.
amplify.yml replaces the console's build settingsIf you've customised the build in the Amplify console, merge your changes into the file.

12. Operations

  • Data: all content is JSON in SPARK_DATA_DIR, written atomically (temporary file, then rename) with version checks, so two people saving the same document can't overwrite each other silently (409 conflict).
  • Backups: before each change, the previous version of a document is copied to data/backups/<key>/; the latest 10 are kept. Back up the whole data and uploads folders regularly too.
  • Logs: on Plesk, the backend's output is in the iisnode/ folder next to app.js. Crashes before start-up go to startup-error.log. Look for [revalidate], [api] and [http] lines.
  • On start-up the backend logs its data folder, uploads folder and allowed CORS origins, and warns when SPARK_SHARED_SECRET is missing or short.

13. Troubleshooting

“Blocked by CORS policy … redirected from http://localhost:3000/api/admin/…”

Cause: BACKEND_URL was a remote http:// address. The server redirected to https://, the redirect reached the browser, and the browser called the backend cross-origin. Browsers remember permanent redirects, so it can continue after the setting is fixed.

Fix: use https:// for a remote backend (now automatic), restart next dev, and clear the browser cache: in DevTools, right-click reload → Empty Cache and Hard Reload, or try a private window.

Changes in the admin don't appear on the site

  • Was the item published? Saving and creating without publish only change the draft.
  • Is SPARK_SHARED_SECRET identical on both sides, and available to the running site on Amplify (see amplify.yml)? Test it: POST {site}/api/revalidate with the header x-spark-secret should return {"revalidated":true}, not 403.
  • Is the backend's FRONTEND_URL the site's real address? Check the backend log for [revalidate] the website answered … or couldn't reach the website.
  • Changes still appear within about 5 minutes thanks to the safety net.

Pictures return 404 through /_next/image

On Amplify, the optimizer can't follow the /uploads forwarding (response header x-amplify-optimized: true). Uploaded pictures must use the backend's full address, and the backend host must be in images.remotePatterns (done in lib/api/backend.ts and next.config.ts). hostname there is a bare host name, without https://. Redeploy the site after changing it.

The backend won't start on Plesk

  • Read startup-error.log. “AUTH_SECRET must be set…”: add a 32+ character AUTH_SECRET to the server's .env.
  • IIS error 500.19 (0x800700b7): a duplicate web.config entry; every <add> must be preceded by a <remove> of the same name.
  • Picture uploads fail but everything else works: sharp isn't installed on the server; run npm ci --omit=dev.

Signed out all the time / 401 everywhere

AUTH_SECRET changed (it signs all tokens), or the clocks are wrong. Sign in again; keep AUTH_SECRET stable.

“Too many failed attempts”

The brute-force brake: wait 15 minutes, or restart the backend (the counters are in memory).

Adding an API endpoint (backend)

  1. Create src/routes/api/…/route.ts; folders like [id] become parameters.
  2. Export GET, POST, … wrapped in handle(); use requireSession(request, "editor") for admin endpoints and readBody(request, schema) for input.
  3. Run npm run routes (or dev/build, which run it).
  4. If it changes published content, call revalidateContent().
